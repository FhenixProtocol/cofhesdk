# ACPs

ACPs (Access Control Permissions, formerly called _permits_) are EIP-712 signatures that authorize decryption of confidential data. The `issuer` field identifies who is accessing the data - the issuer must have been granted access on-chain via `FHE.allow(handle, address)`. When an ACP is used, CoFHE validates it against the ACL contract to confirm that the issuer has access to the requested encrypted handle.

Each ACP includes a sealing keypair. The public key is sent to CoFHE so it can re-encrypt the data for the ACP holder. The private key stays client-side and is used to unseal the returned data. ACPs are stored locally and identified by a deterministic hash of their fields.

ACPs can be used to decrypt your own data (self ACPs), or to delegate your access to another party (sharing ACPs).

:::info
The examples below show two approaches for working with ACPs. The `client.acp` API is the recommended approach -- it automatically signs ACPs with the connected wallet and manages the ACP store. The `ACPUtils` API is a lower-level alternative that gives you direct control over signing and storage.
:::

## When do you need an ACP?

- **`decryptForView`**: always requires an ACP.
- **`decryptForTx`**: depends on the contract's ACL policy for that [handle](/reference/dictionary#handle) (`ctHash` in code).
  - If the policy allows anyone to decrypt, you can use `.withoutACP()`.
  - If the policy restricts decryption, you must use `.withACP(...)`.

## Prerequisites

1. Create and connect a client (see the [client page](./client.mdx)).

ACPs are scoped to a **chainId + account**. The SDK uses the connected chain and account by default.

## Quickstart

The recommended approach is to create (or reuse) a self ACP. Once created, it is stored and set as the active ACP for the connected chain and account.

::::code-group

```ts twoslash [client.acp]
// @noErrors
import { createCofheConfig, createCofheClient } from '@cofhe/sdk/web';
import { chains } from '@cofhe/sdk/chains';
import type { PublicClient, WalletClient } from 'viem';

const config = createCofheConfig({ supportedChains: [chains.sepolia] });
const client = createCofheClient(config);
declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
// ---cut---
await client.connect(publicClient, walletClient);

// Returns the active self ACP if one exists, otherwise creates and signs a new one.
const acp = await client.acp.getOrCreateSelfACP();
```

```ts twoslash [ACPUtils]
// @noErrors
import {
  ACPUtils,
  setACP,
  setActiveACPHash,
} from '@cofhe/sdk/acps';
import type { PublicClient, WalletClient } from 'viem';

declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
// ---cut---
const acp = await ACPUtils.createSelfAndSign(
  { issuer: walletClient.account!.address },
  publicClient,
  walletClient
);

// Manually store and activate the ACP
const chainId = await publicClient.getChainId();
const account = walletClient.account!.address;
setACP(chainId, account, acp);
setActiveACPHash(chainId, account, acp.hash);
```

::::

After this, the active ACP is picked up automatically:

- `decryptForView(...).execute()` uses the active ACP.
- `decryptForTx(...).withACP().execute()` uses the active ACP.

## ACP types

The SDK supports three ACP types:

| Type        | Who signs                                 | Use case                                                  |
| ----------- | ----------------------------------------- | --------------------------------------------------------- |
| `self`      | issuer only                               | Decrypt your own data (most common)                       |
| `sharing`   | issuer only                               | A shareable "offer" created by the issuer for a recipient |
| `recipient` | recipient (and includes issuer signature) | The imported ACP after the recipient signs it             |

Notes:

- An ACP includes a **sealing keypair**. The public key is sent to CoFHE for re-encryption. The private key stays client-side for unsealing.
- ACP `expiration` is a unix timestamp in **seconds**. The default is **7 days from creation**.
- When an ACP is created via `client.acp.*`, it is automatically stored and set as the active ACP for the current chain and account.

## Creating a self ACP

A self ACP lets you decrypt data that was allowed to your address. Use `createSelf` to always create a new ACP, or `getOrCreateSelfACP` to reuse an existing active ACP.

### createSelf

::::code-group

## Sharing ACPs

Sharing ACPs let an issuer delegate their ACL access to a recipient. The recipient can then decrypt the issuer's data without needing their own `FHE.allow`. This flow may be useful for auditors or other parties that need to access data but do not have the ability to grant themselves access.

:::::steps

### Issuer creates a sharing ACP

The issuer creates a sharing ACP specifying the recipient's address. The issuer's signature does not include a sealing key.

::::code-group

```ts twoslash [client.acp]
// @noErrors
import { createCofheConfig, createCofheClient } from '@cofhe/sdk/web';
import { chains } from '@cofhe/sdk/chains';
import type { PublicClient, WalletClient } from 'viem';

const config = createCofheConfig({ supportedChains: [chains.sepolia] });
const client = createCofheClient(config);
declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
declare const recipient: `0x${string}`;
// ---cut---
await client.connect(publicClient, walletClient);

const sharingACP = await client.acp.createSharing({
  issuer: walletClient.account!.address,
  recipient,
  name: 'Share with recipient',
});
```

```ts twoslash [ACPUtils]
// @noErrors
import { ACPUtils } from '@cofhe/sdk/acps';
import type { PublicClient, WalletClient } from 'viem';

declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
declare const recipient: `0x${string}`;
// ---cut---
const sharingACP = await ACPUtils.createSharingAndSign(
  {
    issuer: walletClient.account!.address,
    recipient,
    name: 'Share with recipient',
  },
  publicClient,
  walletClient
);
```

::::

### Issuer exports the ACP

Export the ACP as a JSON blob and share it with the recipient.

```ts twoslash [ACPUtils]
// @noErrors
import { ACPUtils } from '@cofhe/sdk/acps';
import type { ACP } from '@cofhe/sdk/acps';

declare const sharingACP: ACP;
// ---cut---
const exported = ACPUtils.export(sharingACP);
```

:::info
The exported JSON does not contain any sensitive data and can be shared via any channel.
:::
:::warning
Do not share `serialize(acp)` output -- serialization is meant for _local persistence_ and includes the sealing private key.
:::

### Recipient imports and signs

The recipient imports the exported JSON and signs it with their wallet. On import, a new sealing key is generated for the recipient. The recipient's sealing key is the one CoFHE uses for re-encryption. The resulting ACP is stored and set as active.

::::code-group

```ts twoslash [client.acp]
// @noErrors
import { createCofheConfig, createCofheClient } from '@cofhe/sdk/web';
import { chains } from '@cofhe/sdk/chains';
import type { PublicClient, WalletClient } from 'viem';

const config = createCofheConfig({ supportedChains: [chains.sepolia] });
const client = createCofheClient(config);
declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
declare const exported: string;
// ---cut---
await client.connect(publicClient, walletClient);

const recipientACP = await client.acp.importShared(exported);

recipientACP.type;
recipientACP.hash;
```

```ts twoslash [ACPUtils]
// @noErrors
import {
  ACPUtils,
  setACP,
  setActiveACPHash,
} from '@cofhe/sdk/acps';
import type { PublicClient, WalletClient } from 'viem';

declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
declare const exported: string;
// ---cut---
const recipientACP = await ACPUtils.importSharedAndSign(
  exported,
  publicClient,
  walletClient
);

const chainId = await publicClient.getChainId();
const account = walletClient.account!.address;
setACP(chainId, account, recipientACP);
setActiveACPHash(chainId, account, recipientACP.hash);
```

::::

To store the imported ACP without making it active, pass `activate: false`. Decrypts that use the active ACP keep using the current one, and the imported ACP is used only where you pass it, for example `.withACP(recipientACP)`. This fits an app that shows someone else's shared data in one view while the rest of the app keeps using the user's own ACP.

```ts twoslash
// @noErrors
declare const client: import('@cofhe/sdk').CofheClient;
declare const exported: string;
// ---cut---
const recipientACP = await client.acp.importShared(exported, { activate: false });
```

In React, see [ACPs in React](/react/acp).

:::::

## Sharing on-chain

Instead of exporting JSON and sending it over a second channel, the issuer can post the share to the on-chain **ACP share registry**. The recipient discovers it from any cofhesdk-enabled app and imports it directly — no copy-paste.

Configure the registry address per chain:

```ts
const config = createCofheConfig({
  // ...
  acp: {
    sharingRegistry: { 11155111: '0x…' },
  },
});
```

### Issuer shares on-chain

```ts twoslash [client.acp]
// @noErrors
declare const client: import('@cofhe/sdk').CofheClient;
declare const recipientAddress: `0x${string}`;
// ---cut---
const sharingAcp = await client.acp.createSharing({
  issuer: '0x…', // connected account
  recipient: recipientAddress,
});

// posts the signed share payload to the registry
const { txHash, shareId } = await client.acp.shareOnChain(sharingAcp);
```

Only signed sharing ACPs can be posted (same rule as `export()`), and only by their issuer. The issuer can retract a pending share with `client.acp.cancelShare(shareId)`.

### Recipient discovers and imports

```ts twoslash [client.acp]
// @noErrors
declare const client: import('@cofhe/sdk').CofheClient;
// ---cut---
// importable shares addressed to the connected account (unexpired, not revoked)
const incoming = await client.acp.getIncomingShares();

// fills in the recipient's sealing key, signs, stores and activates
// (pass { activate: false } to only store it)
const acp = await client.acp.importFromChain(incoming[0]);

// optionally clean up the on-chain entry afterwards (or decline a share)
await client.acp.dismissShare(incoming[0].shareId);
```

An app that sends these writes through its own transaction path can use the same pieces from `@cofhe/sdk/acps`: `ACP_SHARE_REGISTRY_ABI`, `ACP_REVOKER_ABI`, `toChainShare(acp)` (the registry payload), `computeShareId(acp)` (the id the registry assigns), `readSharesFor` / `readShare` (shares read back from the registry) and `getAclServedAddresses(publicClient, chainId)` (the registry and default revoker the chain ACL serves).

The registry lists only importable shares: expired shares and shares whose underlying acp was revoked are filtered out. Everything posted is cleartext by design (the same data as the exported JSON) — note that posting on-chain makes the issuer→recipient relationship public.

### How the registry keeps a share

The registry keeps in storage only what it checks itself — the share **head**: issuer, expiration, recipient, revoker, and the block of the share's `Shared` event. The full payload and its metadata travel in that event:

```solidity
event Shared(address indexed recipient, address indexed issuer, bytes32 indexed shareId, ACP acp, bytes metadata);
```

`getIncomingShares` reads the heads with `sharesFor` (one call, filtered for expiry and revocation on-chain), then the events with one single-block `getLogs` per block, filtered by the share ids — a query any node answers, however old the block. Contracts keep `isShareValid(shareId)`; they cannot read a share's handles. Removing a share deletes its head; its event stays in its block, and readers no longer find it.

## Labelling a SNAPSHOT share

A SNAPSHOT share (`handles` scope) lists ctHashes only, so the recipient has no way to tell what each one is. The issuer knows it at the moment of sharing, and can post it with the share: one **label** per handle, saying where the value came from in terms the recipient can check against the chain.

- **Stored value** — what a view function of a contract returned at a block, e.g. `confidentialBalanceOf(issuer)`.
- **Event value** — a value carried by one log: its contract, block, transaction, log index and event selector, e.g. the amount of a `ConfidentialTransfer`.
- **Unlabelled** — the issuer chose not to say.

Labels are written once, with the share, and cannot be replaced. The format speaks of contracts, selectors and positions in the chain only; it knows nothing of tokens.

### Posting labels

```ts twoslash [client.acp]
// @noErrors
declare const client: import('@cofhe/sdk').CofheClient;
declare const token: `0x${string}`;
declare const balanceHandle: `0x${string}`;
declare const transferLog: import('viem').Log; // from getLogs / getContractEvents
declare const transferHandle: `0x${string}`;
declare const block: bigint;
// ---cut---
import { confidentialBalanceLabel, eventLabelOfLog } from '@cofhe/sdk/acps';

const sharingAcp = await client.acp.createSharing({
  issuer: '0x…',
  recipient: '0x…',
  handles: [balanceHandle, transferHandle],
});

// one label per handle, in the same order
await client.acp.shareOnChain(sharingAcp, {
  labels: [confidentialBalanceLabel(token, block), eventLabelOfLog(transferLog)],
});
```

`labels` is encoded with `encodeShareMetadata`; an app that encodes itself passes `metadata` (the blob) instead.

### Reading, verifying and describing labels

Each `IncomingShare` carries its `metadata` blob (`0x` when posted without labels). Labels are the issuer's **claim**; check them before relying on them:

```ts twoslash [client.acp]
// @noErrors
declare const client: import('@cofhe/sdk').CofheClient;
declare const token: `0x${string}`;
declare const tokenAbi: import('viem').Abi;
// ---cut---
import { describeShareMetadata } from '@cofhe/sdk/acps';

const [share] = await client.acp.getIncomingShares();

// one item per handle: function / event names and params from the ABIs you pass
const items = describeShareMetadata(share.metadata, share.handles, { [token]: tokenAbi }, { issuer: share.issuer });

// one check per handle: 'verified' | 'mismatch' | 'unverifiable' | 'skipped'
const checks = await client.acp.verifyShareLabels(share, { verify: 'all' });
```

| `verify`          | Checks                               | Requests                                                              |
| ----------------- | ------------------------------------ | --------------------------------------------------------------------- |
| `'all'` (default) | every label                          | one `getLogs` per contract and block, one `eth_call` per stored value |
| `'events'`        | event values only                    | one `getLogs` per contract and block                                  |
| `'none'`          | nothing; trust the labels as written | none                                                                  |

- A **stored value** is checked by repeating the view call at the labelled block: the returned word must be the ctHash. Once no node keeps the state of that block, the check returns `unverifiable` (an archive node is needed for old blocks).
- An **event value** is checked against the log at the labelled block and log index: it must come from the labelled contract and transaction, its topic0 must start with the labelled selector, and the ctHash must be one of its topics or data words. Free nodes answer single-block log queries for blocks years old.

`describeShareMetadata` never fails over a missing ABI: an unknown contract or selector leaves the item in raw form (`function` / `event` is `null`). Event parameter values are not in the label; they arrive with the log.

### Layout

One blob per share, version `0x03`. Contracts, selectors and transactions are listed once; each entry points to them by position. Entries follow the order of the share's handles. Integers are big-endian; sizes in bytes.

```text
blob = version (1)
     | contracts:     count (1), 20 bytes each
     | selectors:     count (1), 4 bytes each      function selectors, and event selectors (first 4 bytes of topic0)
     | transactions:  count (1), 6 bytes each      block (4), tx index (2)
     | entries: one per handle, in the share's order

stored value = 0x00 | contract (1) | selector (1) | block (4) | args                    8 bytes or more
event value  = 0x01 | contract (1) | transaction (1) | log index (2) | selector (1)     6 bytes
unlabelled   = 0xff                                                                     1 byte

args     = 0x00                                 no arguments
         | 0x01                                 one argument: the share issuer
         | 0xff | return word (1) | count (1) | argument, count times
argument = 0x00 | word (32)                     a literal ABI word
         | 0x01                                 the share issuer
```

A real share on Arbitrum Sepolia — two balances and five transfer amounts from four transactions — is 122 bytes:

```text
03                                           version 3
02                                           2 contracts
   389be1eb842290f264a6851f49c0149b8035a052     [0] fUSD
   06a52cf2e0ceafc7d1f522400500ca7f3df18754     [1] fUSDy
02                                           2 selectors
   344ff101                                     [0] confidentialBalanceOf(address)
   67500e8d                                     [1] ConfidentialTransfer(address,address,bytes32)
04                                           4 transactions
   12ba9304 0005                                [0] block 314217220, tx 5
   12ba9307 0008                                [1] block 314217223, tx 8
   12ba9309 000a                                [2] block 314217225, tx 10
   12ba9375 000c                                [3] block 314217333, tx 12

00 00 00 12bb9d0f 01      stored value: fUSD, confidentialBalanceOf(issuer) at block 314285327
00 01 00 12bb9d0f 01      stored value: fUSDy, confidentialBalanceOf(issuer) at block 314285327
01 00 00 001e 01          event value: fUSD, transaction 0, log 30, ConfidentialTransfer
01 00 01 0041 01          event value: fUSD, transaction 1, log 65, ConfidentialTransfer
01 00 02 008a 01          event value: fUSD, transaction 2, log 138, ConfidentialTransfer
01 00 03 006a 01          event value: fUSD, transaction 3, log 106, ConfidentialTransfer
01 01 03 0073 01          event value: fUSDy, transaction 3, log 115, ConfidentialTransfer
```

The last two are the two values of one vault deposit and share its transaction. The fUSDy amount appears in two logs of that transaction (115 and 118); the label names the `ConfidentialTransfer`, and a check against log 118 fails on its selector.

**Limits.** 255 contracts, selectors and transactions per share (one-byte counts and positions); blocks up to 4.29 billion; 65,535 transactions per block and logs per block; stored-value arguments are static 32-byte words only.

**Disclosure.** A label names one log. Where a ctHash appears in several logs, the label points at the one the issuer chose; the recipient learns that log's other parameters too.

## Checking an ACP on-chain

The ACL reverts when an ACP is expired, revoked or wrongly signed. `client.acp.checkAccess` runs the same checks and returns the outcome as a status, so an app can tell the user why instead of catching reverts:

```ts twoslash
// @noErrors
declare const client: import('@cofhe/sdk').CofheClient;
declare const acp: import('@cofhe/sdk/acps').ACP;
declare const ctHash: bigint;
// ---cut---
// the ACP itself
const status = await client.acp.checkAccess(acp);

// the ACP and one encrypted value
const access = await client.acp.checkAccess(acp, ctHash);
```

| Status                                                     | Meaning                                                      |
| ---------------------------------------------------------- | ------------------------------------------------------------ |
| `valid`                                                    | The ACP passes the ACL checks (no handle given).             |
| `allowed`                                                  | The ACP may read the handle.                                 |
| `out-of-scope`                                             | The ACP is valid, but its scope does not cover the handle.   |
| `issuer-not-allowed`                                       | The issuer may not read the handle, so no ACP of theirs can. |
| `expired`                                                  | Past its expiration.                                         |
| `revoked`                                                  | Disabled by its revoker (e.g. `client.acp.revokeACP`).       |
| `invalid-issuer-signature` / `invalid-recipient-signature` | A signature does not match.                                  |

Each check is one view call to the ACL, plus a second only to tell `out-of-scope` from `issuer-not-allowed`. A network error still throws.

## Active ACP management

The SDK tracks all stored ACPs and an **active ACP hash** per `chainId + account`. Creating or importing an ACP via `client.acp.*` automatically stores it and selects it as active, except for sharing ACPs and imports made with `activate: false`, which are only stored.

### List stored ACPs

```ts twoslash

import { createCofheConfig, createCofheClient } from '@cofhe/sdk/web';
import { chains } from '@cofhe/sdk/chains';
import type { PublicClient, WalletClient } from 'viem';

const config = createCofheConfig({ supportedChains: [chains.sepolia] });
const client = createCofheClient(config);
declare const publicClient: PublicClient;
declare const walletClient: WalletClient;
// ---cut---
await client.connect(publicClient, walletClient);

const acps = client.acp.getACPs();
Object.keys(acps);
```

### Read / select the active ACP

```ts twoslash
// @noErrors
import { createCofheConfig, createCofheClient } from '@cofhe/sdk/web';
```

## Persistence and security

- The SDK persists ACPs in a store keyed by `chainId + account`.
- In web and React environments, this store uses `localStorage` under the key `cofhesdk-acps`.
- A stored ACP includes the **sealing private key**. Treat it like a secret.
  - Never share serialized ACPs with other users.
  - To share access, use `ACPUtils.export(...)` which strips sensitive fields.
